# Bug 分级矩阵 · PvZ Lite

> **目的**：给每个 Bug 一个可判定的标签——严重度 + 类别 + 响应 SLA，避免"我觉着挺严重你觉着不严重"的扯皮。
>
> **适用**：个人项目版 SLA，节奏宽松；团队协作后需要重新评估。

---

## 1. 严重度（Severity · S0-S3）

| 级别 | 名称 | 判定标准 | 示例（本项目） |
|---|---|---|---|
| **S0** | 阻断（Blocker） | 无法开始游戏 / 游戏立即崩溃 / 数据丢失不可恢复 | 双击打开白屏；`setState` 抛异常导致 RAF 永久停止；localStorage 写坏导致菜单打不开 |
| **S1** | 严重（Critical） | 核心玩法失效 / 玩家明显卡死 / 违反游戏基本规则 | 卡片冷却永不递减（已修）；波次不推进导致玩不下去；僵尸进屋不结束游戏；通关不解锁下一关 |
| **S2** | 一般（Major） | 有替代路径但体验明显受损 / 数值明显失衡 | 阳光掉落速度太快点不到；某种植物伤害数值明显错误；音效节奏错乱；提示文字错误 |
| **S3** | 轻微（Minor） | 视觉 / 文案 / 边缘情况 / 手感小瑕疵 | 图标轻微偏移；文字字号不一致；某边缘状态下颜色不匹配 |

### 判定树（快速定位）

```
是否无法开始 / 崩溃 / 数据不可恢复？
  ├── 是 → S0
  └── 否 → 是否让核心玩法（种植/攻击/过波/胜负）失效？
              ├── 是 → S1
              └── 否 → 是否有明确替代路径？
                          ├── 有 → 是数值 / 体验明显受损吗？
                          │         ├── 是 → S2
                          │         └── 否 → S3
                          └── 无 → S1
```

## 2. 类别（Category · 7 类）

每个 Bug 打一个主类别 + 可选子标签。

| 类别 | 代码 | 含义 | 典型症状 |
|---|---|---|---|
| **CRASH** | C | 崩溃 / 卡死 | 白屏、黑屏、RAF 停、`console.error` 输出 |
| **LOGIC** | L | 逻辑错误 | 数值不对、状态错乱、胜负判定错、解锁错 |
| **UI** | U | 界面 / 交互 | 点击热区错、布局偏移、按钮不可点、颜色错 |
| **PERF** | P | 性能 | 帧率下降、内存泄漏、长时间运行变慢 |
| **SOUND** | S | 音效 | 无音、错音、重复音、声音过大/过小、自动播放策略拦截 |
| **SAVE** | V | 存档 | 数据丢失、格式错乱、跨浏览器不兼容 |
| **DOC** | D | 文档 / 教程 | README 与实际不符、Playtest 提示缺失 |

> 项目当前无存档实现（README 待办第 3 项），**SAVE 类目前应为空**；出现即视为 S1 起（未来加上后升级关注）。

## 3. 响应 SLA（响应时间 · 个人项目版）

"响应"= 从 Bug 被发现到"确认已复现并写进 issue/回归清单"，不是"修完"。

| 严重度 | 响应 SLA | 修复 SLA | 备注 |
|---|---|---|---|
| **S0** | **立即**（当前工作暂停，先复现） | 当天修完；当天无法修完则回滚或 hotfix | 未复现视为 S1，待复现后再定级 |
| **S1** | **本 sprint** 内响应 | 本 sprint 内修完（PvZ Lite 单 sprint ≈ 1 个 Phase，约 1-2 周） | 若不修则必须给出明确规避方案 + 更新 Playtest 通过标准 |
| **S2** | **下个 sprint** 内响应 | 下个 sprint 内修完，或降级为 S3 并给出理由 | 允许延后，但必须写入 Playtest CONCERNS |
| **S3** | **有空时** | 累计 5 条以上时批量处理 | 允许无限期 |

## 5. 回归测试要求（强制）

### 5.1 S0 / S1 硬性要求

- **必须**新增 1 条回归用例（REG-*）覆盖修复点；
- **必须**跑一遍完整烟雾（10 条）确认无回归；
- **必须**在 Bug 报告里填"关联用例"字段。

### 5.2 S2 / S3 弹性要求

- S2：如果修复影响核心逻辑（state machine / 波次 / 数值），建议加用例；纯视觉修复可豁免。
- S3：默认不加用例，除非同类问题已出现 ≥ 3 次。

### 5.3 Flaky 隔离

- 若某回归用例连续 3 次执行结果不一致（Pass/Fail/Pass 或类似），标记为 **flaky**，从烟雾清单移出，进入"隔离队列"；
- flaky 用例必须给出根因分析（时间依赖？RNG 依赖？）并在下一 sprint 内修复或重写；
- **不允许**在烟雾清单中直接跳过 flaky 用例（会污染 CI 信号）。

## 7. 与 Playtest / 回归的联动

1. **Playtest 发现的 Bug** → 定级 → S0/S1 立即修 + 加 REG 用例 → S2/S3 记 CONCERNS；
2. **回归测试发现的 Bug** → 直接 S1 起（能自动测出说明影响范围确定）；
3. **同类 Bug 3 次以上** → 提炼新陷阱写入 README，或加入烟雾清单；
4. **修复上线后** → Playtest 对应轮次再跑一次确认（尤其 Round 1 与 Round 3）。
