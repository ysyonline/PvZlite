### 1.1 `gridToPos` / `posToGrid`（L232–233）——唯一核心函数

**现状**：
```js
232: function gridToPos(col,row){return{x:GRID_X+col*CELL_W+CELL_W/2,y:GRID_Y+row*CELL_H+CELL_H/2}}
233: function posToGrid(x,y){return{x:Math.floor((x-GRID_X)/CELL_W),y:Math.floor((y-GRID_Y)/CELL_H)}}
```

**改法要点（伪代码，roof-gated）**：
```js
// 新常量（放 L44 ROOF_SLOPE 之后）：逐列 Y 偏移向量，单位=列，乘 STEP 得 px
const ROOF_LIFT = [3,2,1,0,0,0,0,0,0];     // col0 最低(+3档)，col2 与平台差 1 档，col3–8 平台=0；"左低右高"
const ROOF_STEP = 8;                        // 每档 px（可行域见 §5）
function liftCol(c){                        // 关键：越界必须回 0，否则 posToGrid 收到 col=-1 会 NaN
  return (level.roof && c>=0 && c<ROOF_LIFT.length) ? ROOF_LIFT[c]*ROOF_STEP : 0;
}
function gridToPos(col,row){return{x:GRID_X+col*CELL_W+CELL_W/2, y:GRID_Y+row*CELL_H+CELL_H/2 + liftCol(col)}}
function posToGrid(x,y){
  const col=Math.floor((x-GRID_X)/CELL_W);            // ★ 必须"先由 x 定 col"
  return {x:col, y:Math.floor((y-GRID_Y-liftCol(col))/CELL_H)};   // ★ 再减"该列"lift 求 row
}
```

**反解要点（红线，务必按序）**：
1. **先 x 定 col**（列不受 Y 偏移影响）→ 2. **再减 `liftCol(col)`** 求 row。
   - 若顺序写反／漏减 lift → 斜坡列点击会整体错行（差 1 档 ≈ 0.08–0.25 行，肉眼可见的点偏）。
2. **`liftCol` 越界守卫必须有**：`posToGrid` 会收到 `x<GRID_X`（col=-1）或 `x>865`（col=9）——数组越界取到 `undefined*STEP=NaN`，会让 `inGrid` 静默失效、点击穿透。
3. **符号约定**：`ROOF_LIFT` 为**向下偏移（+y）**，故 col0 视觉最低 = "左低右高"。**镜像（左高右低）= 整表取负**（1 个字符）；方向最终由美术草图定，见 §5。

**影响面（自动继承，无需逐点改）**：`gridToPos` 被 8 处调用——`updatePlant` L956（植物位）、`hasZombieAhead` L1052、`updateZombies` L1102（啃食判位）、`drawPlant` L1609/1634/1639、`onClick` 铲除 L693。它们**只读 `pos.x` 或整块 `pos.y`**，改函数即全链路跟随（roof 关 lift=0，故 L1–L4 数值逐字节不变）。

### 1.3 僵尸 y 随 x 变化（沿坡行走）

**y 来源清点**（僵尸的 y **从不落盘**，每次绘制/特效时由 `z.row` 现算）：
- 绘制：`drawZombie` **L1816**（唯一画身体处）。
- 死亡：`killZombie` **L1173**（爆点）+ `spawnCorpseParts` **L1145**（零件基准）。
- 命中/爆炸：`updateProjectiles` L1073、`explodeMine` L1024（判据，非绘制）。

**"斜坡段僵尸与格子错位"问题确认**：存在。若只改格子不改僵尸，僵尸会"浮在阶梯之上/陷在阶梯之下"。必须让僵尸 y 与格子同源。

**改法建议（阶梯 vs 连续，二选一）**：
```js
// 方案 A（严格阶梯，与"格子仍矩形"最一致）：取僵尸当前整数列
function colOfX(x){ return Math.floor((x-GRID_X)/CELL_W); }
y = GRID_Y + z.row*CELL_H + CELL_H/2 + liftCol(colOfX(z.x));
// 方案 B（推荐：实体连续、格子阶梯）：坡上按分数列线性插值 → 僵尸平滑爬坡、不跳档
function liftAtX(x){
  const f=(x-GRID_X)/CELL_W, c=Math.floor(f);
  const a=liftCol(c), b=liftCol(c+1); return a+(b-a)*(f-c);   // 越界由 liftCol 回 0 兜住
}
y = GRID_Y + z.row*CELL_H + CELL_H/2 + liftAtX(z.x);
```
**取舍**：
- **方案 B 推荐**：僵尸行走平滑，无"每跨一列跳 1 档(8px)"的台阶感；代价是僵尸在**两格之间**时其 y 与左右任一格心差 ≤S/2（≤4px），肉眼几乎无感。
- **方案 A** 与"格子矩形"语义最自洽，但**坡上 + 平台交界（col2→col3）会有一记 1 档跳变**，步履读感略顿。
- **交界处**：无论 A/B，col2(1 档) → col3(0 档) 必有 1 档落差——这是"阶梯屋顶"的固有形态，建议**保留**（不做跨列线性拉平），否则会与"格子仍矩形"打架、并逼近 C 档。
- **回归影响**：**零**（probe 不吐僵尸 y；无任何用例断言僵尸 y）。见 §2。

### 1.5 弹道命中判定 `zy`（L991 / L1024 / L1073）在斜坡列的处理

**先回答"会不会被 per-col lift 破坏"**：
- **只要 `zy` 保持"逐行基线"（列无关），三处现式一字不改即不破坏**——它们本就是 `GRID_Y+z.row*CELL_H+CELL_H/2`，**不含列**。
- **破坏点不在 hit 判定，而在"发射 y"**：`updatePlant` 的发射 y 用了 `pos.y`（**L969/970/972/974 直线弹**、**L990 抛物 `sy=pos.y`**），`pos.y` 来自 `gridToPos` → 一旦 `gridToPos` 抬升，**斜列上植物的炮弹发射 y 被抬升**，与"列无关的 hit 基线"产生 `lift` 的持久偏差。若 `|偏差|>32`（命中窗半高），**斜列植物射出的弹将打不中同排平地的僵尸**。

**收口方案（两案均零回归）**：
- **方案 ①（最小·保直线弹行为 = 今日）**：hit 基线（L991/L1024/L1073）**保持列无关**，同时把 5 处**发射 y 从 `pos.y` 改回"行基线"**（`rowBaseY(p.row)`，即把它们写回与今日等价的表达式）。
  - 效果：弹道**逐字节等价今日**，斜坡纯视觉 + 网格映射。代价：斜列上炮弹起点与植物贴图有 ≤3S 的竖直小错位（草皮感）。
  - **这与 GDD/roof-process 既有立场一致**（"直线弹在坡上打不中"是屋顶改造的原意，投手是解法）。**零回归**。
- **方案 ②（一致·弹道随地面列）**：hit 基线（L1024/L1073）与发射基线（L991）改用**实体自身列的 `liftAtX`**。
  - 效果：炮弹与斜列僵尸"对齐命中"；但直线弹 y 恒定→僵尸右移时 zy 递减，炮弹仍只在**发射列附近**命中（本质未变，只是把命中区随列平移）。抛物（cabbage）则是屋顶指定解法，天然吃得下。
  - **零回归**：因为 lift 由 `level.roof` gate，L1–L4 恒 0；L5 的 `REG-ROOF-01` 只断言 `vx===260`、`SMOKE-027` 不注入斜坡弹。

**推荐**：**方案 ①**（改动更小、语义不动、与既有设计叙事一致）；若美术/手感要求"弹从斜格长出"，再升 ②。**两案的回归影响都为零**（理由见 §2）。

**最小改法一句话**：hit 三处 **不改**；把发射 y 的 `pos.y`（5 处）换成行基线（方案①）或 `rowBaseY+LliftAtX`（方案②）。**不引入新命中算法，不动窗口常量 32/42。**

## §2 回归影响清单（最关键）

### 2.2 ★ 明确判断

> **「斜坡设在 col0–2」能避开既有用例的取样热点 → 全部用例完全无感，预期漂移 = 0。**

> 1. **非屋顶用例（L1–L4）**：`level.roof` gate 令 `liftCol≡0` ⇒ `gridToPos/posToGrid/所有 y` **逐字节等价今日** ⇒ **结构性免疫**（含那些点击 col0–2 的 20+ 用例，如 REG-CARD-01/02/03、SMOKE-002/014/016/018/022/023、REG-PLANT-01/02/03 等）。它们**不需要任何平移**。
> 2. **唯二 L5 用例**（`REG-ROOF-01`、`SMOKE-027`）：**均不读 y**（`probe` 不吐 y；注册断言仅 counts/sun/type/vx/文本）。`REG-ROOF-01` 虽点 col2（斜坡），但靠 `gridToPos↔posToGrid` 互逆保证落格正确 ⇒ **无感**。
> 3. **理论唯一暴露点**（仅当**违反 gate 约定**、把 lift 做成**全局无条件**时才出现）：`REG-ZOM-03` 与 `SMOKE-020` 在 **col2/row0** 注入 **flat 豌豆**（y=行基线）去打 col2 僵尸——若 hit 基线改成随列且 **1 档 > 32px**，会 miss ⇒ 该两例挂。
>    - **兜底平移方案（仅在同无条件全局 lift 的非常规实现下才需要）**：把这两例的豌豆/僵尸采样从 col2 挪到 col3（平台），或把注入 y 改成 `行基线+liftCol(col)`。**推荐做法是直接守 gate（`liftCol` 内加 `level.roof` 判定），使此兜底永不触发。**

**结论**：**守 `level.roof` gate + `gridToPos/posToGrid` 严格互逆 ⇒ 漂移 0，无需改任何用例断言。** 门控基线（烟雾 27 · 回归 60 · 总线 56）**预期全绿不变**（SMOKE-027 已内建 L5 render"不抛"守门，新绘制只用 harness 桩已支持的原语，见 §4-R3）。

## §5 参数建议：斜坡每列抬升 px 的工程可行域

### 5.1 约束推导（canvas 高 680 · 屋面底 y=600 · 天空带 90/可见 80）

**既定几何**：`GRID_Y=80`、`ROWS*CELL_H=520` ⇒ **屋面底 = 600**；`CARD_H=78` ⇒ **`CARD_Y = 680-78-2 = 600`**（卡片栏顶 **恰好** 压在屋面底）；天空带 `SKY_H=90`（可见纯天空 0–80）。

**左低右高（本方向）**：`lift(col) = LIFT[col]*S`，`LIFT=[3,2,1,0,…]`，**向下**偏移。col0 顶边 = `80+3S`；col0 底边 = `600+3S`。记 **总坡高 `H=3S`**。

| 约束 | 数学式 | 解 |
|---|---|---|
| **(1) 顶部不裂**（CSS 绿底不露） | `80+3S ≤ 90` | **3S ≤ 10 → S ≤ 3.3px** |
| (1') 若在斜坡列补天空块 | 解除 (1)（+3~6 行） | 仅受 (2)(3) 限 |
| **(2) 底部不出画** | `600+3S ≤ 678`（留 2px） | **3S ≤ 78 → S ≤ 26px** |
| **(3) 左底行不被卡片栏吞没**（视觉） | `3S ≤ ~24` | **S ≤ 8px**（保底行可见 >80%） |
| **(4) 阶梯可读**（每档可辨） | `S ≥ ~6px` | **S ≥ 6px** |

### 5.2 可行域与推荐

- **(1) 与 (4) 直接冲突**：`S≤3.3` 与 `S≥6` **无交集** ⇒ **"不裂口 + 可读斜坡"在本布局下不可能同时满足**。
  ⇒ **结论：可见斜坡的必要前提 = 在斜坡列补一小块天空（或上调 `SKY_H`）**。这不是可选项，是几何硬约束。
- 补天空后可行域：**`S ∈ [6, 8]`（干净）**，可放宽至 **`S ≤ 26`（总坡 78px，但左底行几乎全被卡片栏遮，不建议）**。
- **推荐工程区间：`S ≈ 6–8px`（总坡高 18–24px，每档 6–8px）**；美术若想更陡可上探至 **`S≈12`（总 36px）**，代价是左底行被卡片栏遮 ~36px（约 1/3 行）。
- **镜像方向（左高右低，若美术改主意）**：col0 顶边 `80-3S≥0 → S≤26`，底边 `600-3S` 上移（**无卡片栏遮挡**），但底部出现 CSS 绿缝 → 同样需补色块。**该方向头寸更松（上方 ~80px），但与用户"左低右高"相悖**——列出仅供美术对照。

### 5.3 与美术侧的协调（数值未定，本侧只给可行域）

- 工程侧接口 = **`LIFT=[3,2,1,0,…]`（形状）+ `S`（幅度）+ 方向符号**（3 个自由度）；美术草图只需锁定"**总坡高 H 落在 [18, 78]，推荐 [18, 24] px**"即可，工程反解 `S=H/3`。
- **联动项**：(a) 是否补天空块（H>10 则必须）；(b) 卡片栏是否可被左底行"压边"（决定 H 上限是 24 还是更大）；(c) 与 `ROOF_SLOPE=0.18` 的谐调度（阶梯总高 H 与斜缝 A 同一量级更协调）。
- **不可协商**：`S` 的符号/幅度**不改变** `posToGrid` 反解顺序（始终"先列后行"），也不越过 roof gate。

## §C.1 坐标模型（美术几何 → 工程闭式）

**美术函数**（`slope-bc-art-notes.md` §二）：
```
liftX(x) = 60 · clamp((x − 55) / 270, 0, 1)        // 抬升量（≥0 = 向屏幕上方 = y 减小）
```
**在关键 x 处取值**（实测代入）：

| x | 55 | 100(col0心) | 145 | 190(col1心) | 235 | 280(col2心) | 325 | ≥325 |
|---|---|---|---|---|---|---|---|---|
| liftX(x) | 0 | **10** | 20 | **30** | 40 | **50** | 60 | 60 |

⇒ 坡面（row0 顶边）= `80 − liftX(x)`：**80→60→40→20**（col0左→col1左→col2左→col3左），平台平。**连续、无跳变**。屋面底 = 顶 + 520 → 600→540（右端高）。

**工程映射（C2）**：
```js
function liftX(x){ return 60*Math.max(0,Math.min(1,(x-GRID_X)/270)); }   // GATED: level.roof 才非 0
function gridToPos(col,row){
  const x=GRID_X+col*CELL_W+CELL_W/2;
  return { x, y: GRID_Y+row*CELL_H+CELL_H/2 - liftX(x) };               // 用格心 x
}
function posToGrid(x,y){
  const col=Math.floor((x-GRID_X)/CELL_W);
  return { x:col, y:Math.floor((y-GRID_Y+liftX(x))/CELL_H) };           // ★ 用"点击点实际 x"
}
```
- **符号**：`y_screen = y_flat − liftX(x)`（抬升=减小 y）。
- **gate**：`liftX` 内加 `level.roof ? … : 0`；L1–L4 恒 0 → **逐字节等价今日**。

**实体（僵尸）连续 y**：`y = GRID_Y + z.row*CELL_H + CELL_H/2 − liftX(z.x)`（**连续**，消灭"电梯感"）。

**弹道（必须随抬升）**：hit 基线 `zy = GRID_Y+z.row*CELL_H+CELL_H/2 − liftX(z.x)`；发射 y = 植物格 y（已抬升）。理由见 §C.6-R1。

## §C.5 回归影响（C 档是否仍零漂移）

**结论：C2 同样零漂移。** 逐点核验：

### (a) `gridToPos ↔ posToGrid` 互逆性（连续 lift 下）——**成立，且有闭式解**
- **闭式反解**：`col = floor((x−GRID_X)/CELL_W)`；`row = floor((y − GRID_Y + liftX(x)) / CELL_H)`。**无迭代**（`liftX` 分段线性，一次 clamp）。
- **互逆证明（格心）**：`posToGrid(gridToPos(c,r))` 代入 → `y − GRID_Y + liftX(x)` 恰好 = `r·CELL_H + CELL_H/2`，`floor` = `r`（因 `CELL_H/2 < CELL_H`）⇒ **精确回 (c,r)**，**与 liftX 的具体形状无关**，只要两函数用**同一个 liftX**。
- **任意点**：`row = floor(...)` 正是"视觉平行四边形格的包含判定"⇒ 返回"点所在的斜格"，**语义正确**。
- **逐列常量 vs 连续**：反解复杂度**几乎相同**（连续只多一个 clamp/clamp 分支）；但**逐列常量只能得到矩形格（=B）**，**无法产出平行四边形**——故 C 必须用连续。

### (b) `REG-ROOF-01` 的 `clickGrid(2,2)`（正落斜坡列 col2）——**仍精确落 (2,2)**
代入：`gridToPos(2,2)` → x=280、y=`80+208+52−liftX(280)=340−50=290`；
`posToGrid(280,290)` → col=`floor(225/90)=2`；row=`floor((290−80+50)/104)=floor(260/104)=2` ⇒ **(2,2)** ✓。
该用例断言只读 plants/sun/type/`vx`（无 y）⇒ **通过**。

### (c) `SMOKE-027` T16 的 `clickGrid(4,2)`（平台 col4）——**仍落 (4,2)**
`liftX(370)=60`（平台常量）→ 同理精确回 (4,2)；断言 plants/sun/col/row ⇒ **通过**。L5 render 帧只验"不抛"，新绘制用桩内原语 ⇒ **通过**。

### (d) §2.2 上轮"理论暴露点"（`REG-PULT-01/02`、`SMOKE-020`、`REG-ZOM-03`）——**不被激活**
这四例**均跑在 L1（默认关，未 `setLevel`）**⇒ `liftX≡0` ⇒ `gridToPos/posToGrid/弹道/僵尸 y` **逐字节等价今日** ⇒ **无感**。
（即便命中基线随 x 抬升，L1 的 lift 恒 0 仍恒等。）

### (e) 门控基线
烟雾 27 / 回归 60 / 总线 56 ⇒ **预期全绿不变**（本档零 SFX、零数据、零新卡片）。

> **一句话**：**C 档（C2）回归零漂移成立**；唯一前提仍是"`liftX` 由 `level.roof` gate"+"`gridToPos/posToGrid` 用同一 liftX"。

## §D.2 逐项核算（H=60）

### ① 顶部：城垛是否放得下？**可行，余 8px（城垛 12 定稿口径）**

- 平台顶 y = `GRID_Y − H` = 80−60 = **20**。
- 城垛顶 = 20 − **12（定稿）** = **8**；〔勘误前：20 − 14（美术示意）= 6〕。
- 判据：城垛顶 ≥ 0 ⇒ **H=60 通过**（**余 8px**；美术示意口径为 6px）。

> **结论：H=60 顶部可行。** 这是**唯一的真实约束**。

### ② 顶部是否裂缝（CSS 绿底）？**无裂缝 —— C2 天然消解**

- C2 是**向上抬升**：`col0` 顶边 = `80 − liftX(55)` = **80**（**不动**）；屋顶越往右越高。
- 抬升部（y < 80，横跨斜坡列）**透出的正是现有全宽天空带**（`fillRect(0,0,canvas.width,90)`，L1376）⇒ **左右都不露绿底**。
- 视觉结果：**左侧露天空多（0–80）、右侧露天空少（0–20）**——恰是「左低右高」的正确读感。
- ⇒ **§5 的 (1)「顶部裂缝」约束在本模型下不存在**；**无需在斜坡列补天空块**（任务书此假设基于 B 档向下偏移模型，C2 向上抬升自然消解）。

> **结论：无裂缝、无需补天空。** （若实现后出现 1px 缝，再补一小块 `fillRect` 即可——备选，非默认。）

### ③ 底部：左底行是否被卡片栏吞掉？**不吞**

- `CARD_Y=600` = 屋面底沿 `600` ⇒ **卡片栏顶与屋面底沿齐平、不重叠**。
- col0（未抬升）row4 下沿 = **600**，正好压在齐平线上、**完全可见**（>99%）。
- 抬升列 row4 下沿上移（至 540），其下空档由**檐板 `#463b2b`** 填充至 600 ⇒ **永远不越过 600、不动卡片栏**。
- ⇒ **§5 的 (3)「左底行被卡片栏吞」约束在本模型下不存在**。

> **结论：底部不受约束。**

### ④ 底部是否出画？**不出画**

- 檐板最下沿 = **600** < 678（画布底 −2px）⇒ 通过。
- 屋面最低点 = col0 底 = 600 ⇒ 通过。

## §D.3 ★ 明确回答三个点名问题

### Q1：H=60px 是否可行？**可行。**

逐项核（§D.2）：顶部城垛**余 8px**（城垛 12 定稿口径）✓；无顶部裂缝 ✓；底行不被吞 ✓；不出画 ✓。**H=60 同时满足全部约束。**

### Q2：硬上限？**H ≤ 68px（城垛 12 定稿口径）**；若城垛取美术示意 14 ⇒ **H ≤ 66**。

- 推导：`城垛顶 = 80 − H − 城垛高 ≥ 0` ⇒ `H ≤ 80 − 城垛高`。
  - 城垛 **12（定稿 / 源码现值 L1471）**：**H ≤ 68**。
  - 城垛 14（美术示意）：**H ≤ 66**。
- **绝对硬顶 H ≤ 80**（平台顶触画布上沿 y=0，城垛必然被裁）——不可用。
- **建议留 4~8px 天空余量** ⇒ **实用上限 H ≤ 60~64**。**H=60 落在此区间内，属"接近舒适上限"。**

| H | 平台顶 | 城垛顶(12 定稿) | 判定 |
|---|---|---|---|
| 60 | 20 | 8 | ✅ 可行（余 8） |
| 64 | 16 | 4 | ✅ 可行（余 4，紧） |
| 68 | 12 | 0 | ⚠️ 临界（城垛触顶） |
| 70 | 10 | −2 | ❌ 城垛被裁 |
| 80 | 0 | −12 | ❌ 天空耗尽 |

**建议值 = 60px**（用户已定；保留 8px 余量，距硬上限 68 有 8px 缓冲）。**不建议再上调**（观感收益小、触顶风险大）；**回退阀**：若真机觉平，单常量 `ROOF_LIFT_H` 可提到 **66**（留 2px 余量）。

### Q3：5 列 vs 3 列，可行域放宽还是收紧？**对 H 上限 = 中性；对坡度读感 = 放宽（更缓）。**

- **H 上限与列数无关**：极值（平台顶 20、底沿 600）只由 H 决定（§D.1.1 注）⇒ **3→5 列不移动 H 上/下限**。既非放宽、也非收紧。
- **5 列真正改变 = 坡度更缓**：同 H=60 下，每列增量 20px→**12px**、坡角 12.5°→**7.6°**。⇒ **每列斜切量更小**（平行四边形更接近矩形，C2 落格/绘制更稳），但**坡度观感更subtle**。
- **反推**：若要 5 列达到 3 列的 12.5° 陡度，需 `H = 450·tan12.5° ≈ 100px` ≫ 硬上限 68 ⇒ **5 列本质更缓，无法复刻 3 列陡度**。
- **工程建议**：5 列已天然更缓，**不要再下调 H**（否则坡过subtle、读不出斜）；**保持 H=60**；「偏缓」担忧用**补偿三件套**（半缝/明暗/压条加粗——施工规格 §2.E）缓解。

> **一句话**：**H 上限不动（68，城垛12）；列数改的是"坡的陡缓"，不是"H 的天花板"。5 列 = 更缓、每列斜切更小、落格更稳，但不放宽 H 上限。**
