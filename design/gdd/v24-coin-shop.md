## §1 概述

### 1.1 功能定位

积分商城是金币经济（`points`）的**消费出口**。当前唯一消费点「卡槽解锁」（合计 6400 积分）在 UI 面板下线后处于「逻辑留存、入口缺失」状态，积分长期只进不出。商城将恢复卡槽入口并扩展三类新消费，使积分从「解锁进度计」升级为「可支配货币」。

### 1.2 玩家价值

| 维度 | 价值 |
|---|---|
| **目标感** | 全通 40 关后，积分不再是死数字——有东西可买、有理由重刷 |
| **表达性** | 皮肤系统提供视觉个性化（"我的豌豆射手是黄金版"） |
| **策略深度** | 消耗品在困难关卡提供容错弹性；永久增益给硬核玩家额外追求 |
| **进度感知** | 逐步买满增益 / 集齐皮肤 → 可量化的长线目标 |

### 1.3 MDA 分析

| 层 | 描述 |
|---|---|
| **机制（Mechanics）** | 积分购买 → 即时到账（消耗品入背包 / 增益激活 / 皮肤解锁） |
| **动态（Dynamics）** | 玩家权衡「先买增益加速收益」vs「先买皮肤满足收集欲」vs「囤消耗品应对高难」→ 产生金钱分配策略 |
| **美学（Aesthetics）** | 收集（皮肤图鉴）、挑战（买增益冲高难）、表达（装备皮肤炫耀）、进度（逐步买满商城） |

### 1.4 Bartle 玩家类型映射

| 类型 | 对应消费偏好 |
|---|---|
| **成就者（Achiever）** | 优先买永久增益 → 更快通关高难 → 刷更多积分 |
| **探索者（Explorer）** | 买消耗品试各种关卡组合、解锁全皮肤集齐 |
| **社交者（Socializer）** | 皮肤展示（本作无社交层，暂为自我满足；预留导入/导出可分享皮肤档） |
| **杀手（Killer）** | 买增益最大化输出 → 挑战 expert 全通 |

### 1.5 设计支柱对齐

| 设计支柱 | 商城对齐 |
|---|---|
| **P1 · 爽快塔防** | 消耗品提供"逆风翻盘"瞬间（如波次跳过、阳光包救急）；增益让防线更从容 |
| **P2 · 渐进解锁** | 商城商品随世界进度逐批开放（如皮肤需世界 2 通关后才解锁对应植物皮肤） |
| **P3 · 可重玩性** | 积分消费创造重刷动力（"再通一轮就能买那个皮肤了"） |

### 1.6 范围分层

| 层 | 内容 | 触发条件 |
|---|---|---|
| **MVP（v2.4.0 必须）** | ① 卡槽解锁（恢复 UI 入口）② 四种永久增益 ③ 三种消耗品 ④ 商店 UI | 初始需求 |
| **目标（v2.4.x）** | ⑤ 皮肤系统（每植物 1–2 款基础皮肤）⑥ 皮肤装备 UI | MVP 验证后 |
| **愿景（v2.5+）** | ⑦ 皮肤扩展包（节日主题、联动）⑧ 消耗品批量购买 ⑨ 皮肤图鉴页面 | 用户后续拍板 |

## §2 商品类别详细设计

### 2.1 类别一：卡槽解锁（slot-unlock）

#### 2.1.1 概述
复用既有 `buySlot()` 函数逻辑，仅恢复 UI 入口。**不改代码逻辑**，只加按钮。

#### 2.1.2 机制
| 字段 | 值 |
|---|---|
| 商品 ID | `slot-7` / `slot-8` / `slot-9` / `slot-10` |
| 价格 | 600 / 1200 / 1900 / 2700（引用 `SLOT_CONFIG.SLOT_PRICE`） |
| 前置 | 前一槽已解锁 |
| 上限 | 10 槽（`SLOT_CONFIG.maxSlots`，卡栏布局硬上限） |
| 已满时 | 显示「已满 · 10 槽」灰色不可点击 |
| 实现 | 点击 → `buySlot()` → `saveMeta()` → toast 反馈 → 刷新商店显示 |
| 存档键 | 复用 `pvz_slots`（不新增） |

#### 2.1.3 数据来源
```js
// 只读引用，不改：
SLOT_CONFIG.SLOT_PRICE // {7:600, 8:1200, 9:1900, 10:2700}
SLOT_CONFIG.maxSlots   // 10
```

#### 2.1.4 边缘情况
- **EA-1**：玩家有 700 积分，第 7 槽 600 已买，第 8 槽 1200 不够 → 第 8 槽按钮显示红色价格 + 不可点击 + hover 提示「积分不足」
- **EA-2**：玩家已解锁 10 槽 → 卡槽区显示「已满 10/10」，不再渲染购买按钮
- **EA-3**：旧档 `pvz_slots=0` 或缺失 → `loadMeta()` 已有 `slots=(sRaw>=1&&sRaw<=10)?sRaw:6` 守卫，默认 6，商城区按此正确渲染

### 2.2 类别二：植物皮肤/装扮（plant-skins）

#### 2.2.1 概述
**纯装饰系统**——不改变植物数值，仅替换视觉外观。玩家购买后可在选卡前或独立界面中装备/卸下皮肤，装备后对战画面绘制走皮肤变体路径。

#### 2.2.2 皮肤定义模型
```js
// 皮肤元数据（配置表新增 SKIN_CATALOG，收拢在 SLOT_CONFIG 近邻或独立顶层常量）
{
  id: 'pea_gold',             // 唯一标识（plantType + '_' + skinVariant）
  plantType: 'pea',           // 适用植物
  name: '黄金豌豆射手',        // 显示名
  desc: '金色涂装的豌豆射手，依然射出绿色豌豆', // 描述（含非功能性声明）
  price: 300,                 // 积分售价
  tier: 'common',             // 稀有度：common / rare / epic（影响价格与边框色）
  unlockReq: null,            // 解锁前置（null=无条件；'world2'=通关世界2后解锁购买权）
}
```

#### 2.2.3 首批皮肤提案（MVP 8 款）

| ID | 植物 | 名称 | 描述 | 稀有度 | 价格 | 解锁条件 |
|---|---|---|---|---|---|---|
| `pea_gold` | pea | 黄金豌豆射手 | 闪耀的金色涂装 | common | 200 | 无 |
| `pea_shadow` | pea | 暗影豌豆射手 | 暗紫配色，瞳孔发红 | rare | 400 | 世界 2 通关 |
| `sunflower_honey` | sunflower | 蜜糖向日葵 | 橙黄色花瓣，产出蜂蜜色阳光 | common | 200 | 无 |
| `nut_iron` | nut | 铁壁坚果 | 灰铁质感涂装 | common | 250 | 无 |
| `melon_jade` | melon | 翡翠西瓜 | 翠绿外皮，淡绿瓜瓤 | rare | 500 | 世界 3 通关 |
| `cherry_phantom` | cherry | 幽灵樱桃 | 半透明淡蓝外观 | rare | 450 | 世界 2 通关 |
| `snowpea_aurora` | snowpea | 极光寒冰射手 | 蓝紫渐变 + 雪花粒子 | epic | 800 | 世界 4 通关 |
| `cabbage_autumn` | cabbage | 秋叶卷心菜 | 橙红暖色，落叶飘落 | common | 200 | 无 |

#### 2.2.4 皮肤系统工作流

```
购买 → pvz_skins.owned 加入该 ID → 已拥有标记
装备 → 选卡界面或独立「装扮」页 → 点击皮肤 → pvz_skins.equipped[plantType] = skinId
对战 → drawPlant() 检测 equipped[plant.type] → 走对应皮肤绘制分支
卸下 → equipped[plantType] = null → 恢复默认外观
```

#### 2.2.5 皮肤绘制实现策略

**最小改动方案**：在 `drawPlant()` 的每种植物绘制块头部插入皮肤判定——

```js
const skin = equippedSkins[plant.type];
if (skin === 'pea_gold') { /* 改 fillStyle 为 #ffd700 系列 */ return; }
// 否则走默认绘制
```

**绘制成本**：每种皮肤约 10–20 行 Canvas 代码（改色/加装饰），首批 8 款约 80–160 行。

#### 2.2.6 存档字段

| 键 | 类型 | 示例 | 说明 |
|---|---|---|---|
| `pvz_skins` | JSON 字符串 | `{"owned":["pea_gold","nut_iron"],"equipped":{"pea":"pea_gold"}}` | 拥有集合 + 装备映射 |

#### 2.2.7 边缘情况
- **EB-1**：玩家拥有皮肤但没有对应植物 → 可购买但不可装备（绘画跳过），商店显示「需先解锁植物」
- **EB-2**：旧档无 `pvz_skins` 键 → `loadMeta()` 默认 `{owned:[],equipped:{}}`，无感迁移
- **EB-3**：导出存档包含皮肤数据 → `exportSave()` 自动收集 `pvz_skins`（已有 `pvz_*` 前缀规则覆盖），导入后正常恢复
- **EB-4**：卸载植物皮肤后该植物恢复默认 → `equipped[plantType]` 设为 `null` 或 delete
- **EB-5**：测试模式 `?test=1` → 内存态 `owned` 全皮肤解锁但不写档（走 `saveMeta` 守卫）

### 2.3 类别三：关卡消耗品（consumables）

#### 2.3.1 概述
一次性道具，在关卡对战中使用，用后即扣。**批量购买**（愿景）> 单次购买（MVP）。

#### 2.3.2 消耗品清单（MVP 3 种）

| ID | 名称 | 描述 | 价格（积分） | 最大持有 | 使用时机 |
|---|---|---|---|---|---|
| `replay_ticket` | 重玩门票 | 允许重玩已通关关卡（消耗品版；免费关卡本身可无限重玩，本券为「额外奖励门票」——重玩时额外 +50% 积分收益） | 80 | 99 | 选关页，开始重玩前 |
| `wave_skip` | 波次跳过 | 立即结束当前波次，所有场上僵尸清退，下一波正常刷新（BOSS 波/最终波不可用） | 100 | 5 | 对战中任意时刻 |
| `sun_pack` | 阳光补给包 | 立即获得 150 阳光（可突破阳光上限） | 50 | 10 | 对战中任意时刻 |

> **设计备注**：`replay_ticket` 的定位需要谨慎。当前重玩已通关金币关已有 `RETAIN_COIN_RATIO=50%` 机制。若门票是「允许重玩」的门禁，会与现有自由重玩设计冲突。MVP 阶段建议门票定位为**收益加成券**而非准入券。若用户倾向门票=准入制，可在拍板时调整。

#### 2.3.3 使用流程

```
对战中 → 点击 HUD「道具」按钮（新增） → 弹出小型消耗品面板（2×2 或列表）
       → 点击某消耗品 → 确认提示「使用 阳光补给包？」 → 确认 → 效果生效 → 数量 -1 → saveMeta()
       → 关闭面板 → 继续对战
```

#### 2.3.4 对战 HUD 道具按钮布局

| 字段 | 建议值 |
|---|---|
| 位置 | 右上角暂停按钮旁（约 x=920, y=8）或底部状态栏右侧 |
| 尺寸 | 32×32 或 40×28 |
| 图标 | 🎒 或文字「道具」 |
| 快捷键 | `I` 或 `B`（不与现有 1-6/X/Space/F/M/R/Esc 冲突） |
| 消耗品面板 | 居中弹出 240×180 半透明面板，列出持有消耗品 + 数量 + 使用按钮 |

#### 2.3.5 存档字段

| 键 | 类型 | 示例 | 说明 |
|---|---|---|---|
| `pvz_consumables` | JSON 字符串 | `{"sun_pack":3,"wave_skip":1,"replay_ticket":5}` | 持有数量（缺省=0） |

#### 2.3.6 边缘情况
- **EC-1**：对战中使用波次跳过但当前为最终波 → 按钮灰色 + hover 提示「最终波不可跳过」
- **EC-2**：对战中使用波次跳过但当前为 BOSS 波（猫王波） → 同 EC-1，BOSS 波不可跳过
- **EC-3**：阳光补给包使阳光超过显示上限 → 允许突破（`sun` 变量无上限约束，仅种植 cost 检查）
- **EC-4**：道具数量为 0 → 道具面板该项灰色，显示「×0」
- **EC-5**：道具面板打开时暂停游戏 → 打开面板时设 `paused=true`，关闭恢复（与现有暂停逻辑对齐）
- **EC-6**：快捷使用道具后游戏恢复 → 若有快捷键直接使用 sun_pack（如按 `B`），则无需打开面板，效果即时生效 + toast 反馈

### 2.4 类别四：局内永久增益（permanent-upgrades）

#### 2.4.1 概述
**一次性购买、永久激活**的被动增益。购买后对所有关卡/难度永久生效。不可堆叠、不可退款。

#### 2.4.2 增益清单（MVP 4 种）

| ID | 名称 | 描述 | 价格 | 效果 | 前置 |
|---|---|---|---|---|---|
| `upg_sun_start` | 阳光起步 | 每局初始阳光 +50 | 500 | `sun` 初始值从 50 → 100 | 无 |
| `upg_sun_bonus` | 阳光红利 | 向日葵/阳光菇每次产出 +5（25→30 / 15→20） | 1200 | 产阳光处 `.amount+=5` | `upg_sun_start` 已购买 |
| `upg_cd_1` | 冷却加速 I | 所有植物冷却时间 -10% | 800 | `cardCD` 基数 × 0.9 | 无 |
| `upg_cd_2` | 冷却加速 II | 所有植物冷却时间 -20%（覆盖 I） | 1500 | `cardCD` 基数 × 0.8 | `upg_cd_1` 已购买 |

> **设计备注**：增益数值保持克制。+5 阳光/次、-10%/20% CD 已有感知但不颠覆平衡。定价参照卡槽斜率——第一个增益 500（接近第 7 槽 600），最后一个 1500（接近第 9 槽 1900）。

#### 2.4.3 效果实现点

| 增益 | 实现位置 | 改动量 |
|---|---|---|
| `upg_sun_start` | `startLevel()` 或 `newGame()`，`sun` 初始赋值处 | 1 行 |
| `upg_sun_bonus` | `updatePlant()` 中 sunflower/sunshroom 产阳光处 | 2 行 |
| `upg_cd_1` / `upg_cd_2` | `placePlant()` 设 `cardCD[type]` 处，乘以 `getUpgradeCDMultiplier()` | 1 行 + 1 函数 |

#### 2.4.4 存档字段

| 键 | 类型 | 示例 | 说明 |
|---|---|---|---|
| `pvz_upgrades` | JSON 字符串数组 | `["upg_sun_start","upg_cd_1"]` | 已激活的增益 ID 列表（只存 ID，不缺省=未激活） |

#### 2.4.5 边缘情况
- **ED-1**：玩家购买 `upg_cd_2` 时已拥有 `upg_cd_1` → `upg_cd_2` 覆盖 `upg_cd_1` 效果（不叠加），存档中两者同时存在但 `getUpgradeCDMultiplier()` 只取最高级
- **ED-2**：测试模式 → 所有增益内存态激活但不写档
- **ED-3**：旧档无 `pvz_upgrades` 键 → `loadMeta()` 默认 `[]`，不影响现有体验
- **ED-4**：增益对 bot（自动战斗）的影响 → 需确认 bot 逻辑是否读取增益，若不读则 bot 强度不变（暂按**不读**处理，bot 走裸参数，保持挑战性）

## §3 商店 UI 交互流

### 3.1 状态机扩展

```
现有状态：menu → select → deck → play → end
新增状态：shop（从 menu 进入，返回 menu）
```

`state` 变量新增合法值 `'shop'`。

### 3.2 入口

```
主菜单（drawMenu）
  ├─ 「进入游戏」钮（MENU_BTN，x=380 y=400 240×56）
  ├─ 「商店」钮（新增 SHOP_BTN，建议 x=380 y=468 240×48）  ← 新增
  ├─ 导出/导入（不变）
  └─ 版本号（不变）
```

**按钮常量**：
```js
const SHOP_BTN = { x: 380, y: 468, w: 240, h: 48 };
```

## §4 存档结构设计

### 4.1 现有存档键（不变）

| 键 | 类型 | 用途 |
|---|---|---|
| `pvz_points` | number string | 积分 |
| `pvz_slots` | number string | 已解锁槽数 |
| `pvz_cards` | JSON string[] | 已拥有植物卡 |
| `pvz_deck` | JSON string[] | 当前卡组 |
| `pvz_clears` | number string | 累计通关次数 |
| `pvz_diff_clears` | JSON object | per-difficulty 通关记录 |
| `pvz_progress_v2` | JSON object | v2 进度（cleared/unlocked） |
| `pvz_progress_v3` | JSON object | v3 三难度独立进度 |

### 4.2 新增存档键

| 键 | 类型 | 默认值 | 示例 | 写盘时机 |
|---|---|---|---|---|
| `pvz_skins` | JSON 字符串 | `'{"owned":[],"equipped":{}}'` | `'{"owned":["pea_gold"],"equipped":{"pea":"pea_gold"}}'` | 购买皮肤 / 装备/卸下皮肤 |
| `pvz_consumables` | JSON 字符串 | `'{}'` | `'{"sun_pack":3,"wave_skip":1}'` | 购买消耗品 / 使用消耗品 |
| `pvz_upgrades` | JSON 字符串数组 | `'[]'` | `'["upg_sun_start","upg_cd_1"]'` | 购买增益 |

### 4.3 `loadMeta()` 扩展

```js
// 新增三行读档（在 loadMeta 末尾追加）
const skinRaw = storageGet('pvz_skins');
const skinsData = skinRaw ? JSON.parse(skinRaw) : { owned: [], equipped: {} };
ownedSkins = Array.isArray(skinsData.owned) ? skinsData.owned : [];
equippedSkins = (skinsData.equipped && typeof skinsData.equipped === 'object') ? skinsData.equipped : {};

const consRaw = storageGet('pvz_consumables');
consumables = consRaw ? JSON.parse(consRaw) : {};
if (typeof consumables !== 'object') consumables = {};

const upgRaw = storageGet('pvz_upgrades');
upgrades = upgRaw ? JSON.parse(upgRaw) : [];
if (!Array.isArray(upgrades)) upgrades = [];
```

### 4.4 `saveMeta()` 扩展

```js
// 在 saveMeta 内追加三行
storageSet('pvz_skins', JSON.stringify({ owned: ownedSkins, equipped: equippedSkins }));
storageSet('pvz_consumables', JSON.stringify(consumables));
storageSet('pvz_upgrades', JSON.stringify(upgrades));
```

### 4.5 存档迁移

- **旧档无新键**：`loadMeta()` 默认值处理，无感迁移。玩家首次进商店时一切为空。
- **导出/导入兼容**：`exportSave()` 自动收集 `pvz_skins` / `pvz_consumables` / `pvz_upgrades`（已有 `pvz_*` 前缀泛收集规则），导入端同样覆盖恢复。**不需额外代码**。
- **回滚兼容**：若未来版本回滚至 v2.3.x，三个新键静默残留——不影响旧版运行（旧版不读它们），也不会被旧版 `saveMeta` 覆盖（旧版不写它们）。

## §5 经济平衡

### 5.1 积分收支全景

#### 5.1.1 收入端（既有，不变）

> **口径**：下表为 2026-10-01 主理人从源码波表逐关累加的**实测理论值**（通关 = 杀光全部波次僵尸），非估算。

| 来源 | normal 全通值 | 说明 |
|---|---|---|
| 击杀掉落 | **2,644** | 40 关 × 波表僵尸 × 阶位值（铜1/银2/金3），含猫王本体+伴舞 |
| 金币关首通 | **2,400** | 24 关 × 100（仅一次） |
| 世界通关 | **1,200** | 4 世界 × 300（仅一次） |
| **normal 全通理论总收益** | **6,244** | 三者之和（实测） |

> **分世界明细**（normal，击杀掉落+金币首通+世界通关）：
> 世界1=841 ｜ 世界2=1,406 ｜ 世界3=2,097 ｜ 世界4=1,900。

> **重通收益**：金币关重通 24 关 × 50 = **1,200/轮**（击杀掉落分亦重发，实际重通每轮略高于此）。

#### 5.1.2 支出端（新增）

| 类别 | 总价范围 | 说明 |
|---|---|---|
| 卡槽解锁 | 6400（已存在） | 第 7–10 槽 |
| 永久增益（4 项） | 4000 | 500 + 800 + 1200 + 1500 |
| 消耗品（循环） | 无上限 | 每次 50–100 |
| 皮肤（8 款 MVP） | 3000 | 200×3 + 250 + 400 + 450 + 500 + 800 |

**全部买断总价（MVP）**：6400 + 4000 + 3000 = **13,400 积分**

#### 5.1.3 玩家时间线推算（normal，基于实测 6,244）

| 阶段 | 积分结余（normal） | 可消费项 |
|---|---|---|
| 通 1 个世界 | ≈ 841 | 半个增益 + 若干消耗品 |
| 通 2 个世界 | ≈ 2,247 | 卡槽第 7 槽（600）+ 增益 1 个 |
| 通 3 个世界 | ≈ 4,344 | 卡槽第 7-8 槽（1800）+ 增益 2 个 |
| 全通（4 世界） | ≈ 6,244 | 卡槽 3 个（3700）+ 增益 2 个 |
| 重刷 1 轮 | +1,200+ | 补齐卡槽第 10 槽 / 增益 |
| 全部买断（13,400） | — | 需重刷约 6 轮，或打 hard/expert 加速 |

> **关键判断（实测修正）**：normal 全通 6,244 距卡槽 6400 仅差 **156 分**——差一点买不起最后一槽，处于「逼玩家重刷一轮」的微妙位置，符合原版 PvZ 研磨节奏。增益（4000）与皮肤（3000）属后续追求，靠重刷或高难度获取。

> **⚠️ 历史勘误**：本表取代早期「全通约 2000-3000」的立项估算（漏算了击杀掉落分 2,644）。GDD 首版 6000-7000 区间实为正确口径。

### 5.2 价格锚定策略

> **锚点参照系**：normal 全通 **6,244 分**（实测），卡槽 6400 差 156 → 重通 1 轮 1200+ 溢出。以下价格以此为参照。

| 锚点 | 价格 | 占全通% | 定位 |
|---|---|---|---|
| 第 7 槽 | 600 | 9.6% | 最廉价「必买」参照 |
| 第 10 槽 | 2700 | 43.2% | 最昂贵「必买」参照——全通差一步才够 |
| 增益 `upg_sun_start` | 500 | 8.0% | 低于第 7 槽，「试试水」入门 |
| 增益 `upg_cd_2` | 1500 | 24.0% | 分量级，约全通 1/4 |
| 普通皮肤 | 200–250 | 3.2–4.0% | 冲动消费品，用零钱买 |
| 稀有皮肤 | 400–500 | 6.4–8.0% | 有门槛的收藏 |
| 史诗皮肤 | 800 | 12.8% | 炫耀品 |

### 5.3 通货膨胀防护

- **所有价格写死在常量表**，不出动态市场机制（单机游戏不需要）
- **积分产出唯一管道**（`settleRun`），不新增产出——支出端扩展，收入端锁定
- **重玩减半机制**（`RETAIN_COIN_RATIO=0.5`）防止刷分，长期重刷效率递减但永不归零
- **无退款/无二级市场**——购买即锁定，防止价格套利

## §6 与既有系统的衔接

### 6.1 `buySlot()` 复用

| 项 | 决策 |
|---|---|
| 函数体 | **不动**。`buySlot()` 保持现有 7 行逻辑不变 |
| 调用点 | 商店页的「卡槽」区点击购买 → `buySlot()` |
| `saveMeta()` | `buySlot()` 内部已调用，无需重复 |
| 运行时变量 | `points`、`slots` 均全局变量，商店页直接读 |

### 6.2 `pick` 规则（积分掉落拾取）

**不新增拾取规则**。商店只消费既有 `points`，不对 `pointDrops` / `runPoints` / 拾取判定做任何改动。

### 6.3 选卡界面（`deck` state）

皮肤装备入口可放置于选卡界面：卡面右键 / 下方小按钮 → 弹出皮肤选择器。**MVP 阶段暂不耦合**，皮肤装备在商店内完成（「皮肤」页签既是购买也是装备），降低选卡界面改动风险。

### 6.4 测试模式兼容

| 模块 | 测试模式行为 |
|---|---|
| 商店页 | 可进入浏览，但购买不写档（`saveMeta` 守卫：`testMode` 全键跳过） |
| 皮肤 | 内存态全部解锁但 `?test=1` 结束即消失 |
| 增益 | 同上 |
| 消耗品 | 同上 |
| 表现 | HUD 右上角保留「测试模式」角标（既有逻辑） |

### 6.5 与 `settleRun()` / `saveMeta()` 的时序

```
对局胜利
  → settleRun(won=true)
    → points += total        // 积分到账
    → saveMeta()             // 全局落盘（含 points + 新 pvz_consumables/pvz_upgrades/pvz_skins）
    → setState('end')
  → 结算页 → 返回主菜单 → 商店 → 看到最新积分
```

购买时：
```
商店购买 → points -= price → saveMeta() → toast → 刷新商品状态
```

时序无冲突——购买和结算共用 `saveMeta()`，每次调用全量落盘。

### 6.6 对 `startLevel()` / `newGame()` 的影响

| 增益 | 注入点 |
|---|---|
| `upg_sun_start` | `startLevel()` 中 `sun = 50` → `sun = 50 + (upgrades.includes('upg_sun_start') ? 50 : 0)` |
| `upg_cd_1/2` | `placePlant()` 中 `cardCD[type] = originalCD * getUpgradeCDMultiplier()`（新增函数） |
| `upg_sun_bonus` | `updatePlant()` 向日葵/阳光菇产阳光处 `amount += (upgrades.includes('upg_sun_bonus') ? 5 : 0)` |

函数签名变更：`startLevel()` 和 `newGame()` 不需要新参数——`upgrades` 是全局变量，内部直接读。

## §8 已知风险

### 8.1 设计风险

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R-1 | **积分通胀**：新增消费出口后玩家抱怨「积分不够花」 | 中等——可能引发负面体验 | 价格可调，全部写在常量表；首版上线后观察 1–2 周再微调 |
