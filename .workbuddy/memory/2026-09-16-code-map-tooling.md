# PvZ Lite · 代码地图工具化（2026-09-16）

## 做了什么

用户提出疑问：单文件架构随迭代变大，是否每次改动都浪费 token。先量化分析，再按用户拍板的方案 A 落地了**代码地图工具**。

## 关键结论（量化）

源文件现状：`plants-vs-zombies.html` = 65 KB / **1,716 行** / 56 个顶层函数 / 39 个顶层常量 ≈ **1.9 万 token**

| 改动方式 | token 成本 | 是否随文件增长 |
|---|---|---|
| 定位式小改（Grep 定位 + 读 30 行窗口 + 精确 Edit） | ~1.2k | ❌ 基本恒定 |
| 全文读取（接手诊断 / 跨区重构 / 委托成员施工） | ~19k（翻倍后 38k） | ✅ 线性增长 |

**核心判断**：token 消耗与文件大小不成正比，与「改动方式」成正比。今天真正的消耗大头是 Step 3 委托成员跨全文件施工（6 个特性，约 40-80k），微调只占很小一部分。

## 交付物

| 文件 | 说明 |
|---|---|
| `tools/gen-code-map.mjs` | 生成器（纯读取，不改游戏文件）。`node tools/gen-code-map.mjs` |
| `docs/code-map.md` | 产物：11 分区 → 行号区间 → 逐区成员表（函数/常量 + 说明）+ 高频改动速查表 |
| `README.md` | 新增硬规则：先查表定位 → 只读目标区块 → 精确编辑，禁止全文通读 |

行号采用 **HTML 文件内绝对行号**，可直接作为 `Read(offset, limit)` 参数，与 `Grep` 结果天然对齐。

## 用户决策

- 只做 A（代码地图），**暂不做** B（配置外置 + 构建内联）、C（源码全面拆分）
- C 的触发时机：**要加第三关 / 新植物僵尸等新内容时**再评估（那时跨区改动面铺开，收益最大）

## 踩坑

- 分区区间计算不能用「下一条顶层声明的位置」，必须用「下一分区标题前一行」，否则每个分区都会退化成 1 行
- 分区标题注释会被误识别为成员说明，需要正则过滤 `// ===== xxx =====` 形式的行

## 待办

- 后续每次改完游戏代码，记得重跑生成器刷新行号（行号会因插入而漂移）
- 若要上方案 C，需先出 ADR-005（开发多文件 + 发布单文件）并适配 `tests/harness` 的取源路径
